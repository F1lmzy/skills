# Rust performance experiments

The benchmark runner decides whether a patch wins. A static smell, a passing test, or a lower point estimate alone is not evidence of a speedup. The configured `min_speedup` is an acceptance gate, not a stopping point: accepted trials stack, so keep iterating until measured gains converge.

1. **Define and freeze the contract.** Identify the primary workload and the workloads that must not regress. For new code, write a simple correct version and a reference or differential integration test against a known-good implementation. Use diverse and adversarial inputs — unusual shapes, skewed and degenerate data, both small and large — not just scaled-up happy paths, and test errors, edge cases, and numerical tolerances as applicable. Validate output in tests; make sure benchmarks consume real results. Benchmarks MUST be independent: disable any caching or state shared between them, or a "win" may only exploit a warm fixture. Configure `rustperf.toml` (see `README.md`) before the baseline. Commit it with `Cargo.lock`, tests, fixtures, benchmarks, and source. Do not commit user changes without permission.

2. **Measure before editing.** From a clean Git checkout, run `python3 <SKILL_DIR>/rustperf.py --repo <crate-repo> --session <name> baseline`. NEVER run benchmarks in parallel or alongside other heavy builds; they will compete for resources and the results are invalid. If there is no credible benchmark or correctness contract, build them first rather than claiming a speedup.

3. **Hypothesize narrowly first.** Before each trial, review `status` and do not resubmit a rejected hypothesis unchanged. Identify the hot path under the primary workload. Prefer eliminating algorithmic work, allocations, traversals, or poor memory access to adding complexity. Keep each patch narrow so a win or regression is attributable to one idea. Do not add `unsafe`, change build flags or dependencies, change outputs/work performed, or optimize for fixture identity. If the harness can spawn read-only reviewer agents, consult several at once with DISTINCT prompts — one per hypothesis family (algorithmic work, memory layout, allocation, I/O) — and re-consult them after accepting a patch; reviewers MUST NOT run benchmarks or edit files.

4. **Run and interpret a trial.** `python3 <SKILL_DIR>/rustperf.py --repo <crate-repo> --session <name> trial --hypothesis '<work removed and why it should help>'`. The runner snapshots only allowlisted changes on top of the baseline commit, runs release tests, and compares new Criterion results to both the baseline and incumbent. Keep accepted patches. On a clear rejection, undo only your trial edits; on noise, rerun if the budget warrants it. NEVER edit benchmark inputs, the runner, or its state to get a passing result. Reducing the work performed or weakening a check to pass a gate is cheating even when the gate passes.

5. **Escalate when incremental ideas run out.** Once the log shows repeated rejections or ratio bounds overlapping 1.0, conventional tweaks are unlikely to clear the remaining gap. You have explicit permission and encouragement to attempt a fundamental redesign of the hot path: a different algorithm, data layout, memoization or intermediate caches, SIMD, fused or restructured control flow — as its own trial under the same gates. A re-tuned constant or hyperparameter is not a fundamental change; do not offer one as the next idea. Changing dependencies or build settings requires amending `Cargo.toml` and `rustperf.toml`; ask the user to widen the allowlist rather than bypassing it.

6. **Clean up after convergence, optionally.** When accepted gains fall within noise for disproportionately large diffs, you may run a refactor trial: deduplication and splitting of oversized files, comments kept intact, accepted only at zero regression on the primary workload. The same trial gates apply.

7. **Stop and report.** Stop when a full pass yields only gains within noise (bounds overlapping 1.0) for disproportionately large diffs, at the trial budget, or when the remaining plausible changes do not justify the cost or complexity. `status` shows all trials and the best accepted result. Report the workloads, absolute baseline and final times, speedup, correctness checks, rejected ideas worth knowing, and any trade-offs or remaining uncertainty. Do not extrapolate beyond measured inputs and targets.
